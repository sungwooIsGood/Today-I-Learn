# 카프카 기본

## 카프카 성능

- **파티션 파일은 OS 페이지 캐시를 사용**
    - 파티션에 대한 파일 IO를 메모리에서 처리
    - 서버에서 페이지 캐시를 카프카만 사용해야 성능에 유리
- **Zero Copy**
    - 디스크 버퍼에서 네트워크 버퍼로 직접 데이터 복사
- **컨슈머 추적을 위해 브로커가 하는 일이 단순**
    - 메시지 필터, 메시지 재전송과 같은 일은 브로커가 하지 않음. 프로듀서, 컨슈머가 직접 함
    - 브로커는 컨슈머와 파티션 간 매핑 관리
- **묶어서 보내기, 묶어서 받기(batch)**
    - 프로듀서: 일정 크기만큼 메시지를 모아서 전송 가능
    - 컨슈머: 최소 크기만큼 메시지를 모아서 조회 가능
- **처리량 증대에 따른 확장이 쉬움**
    - 1개 장비의 용량 한계 → 브로커 추가 및 파티션 추가
    - 컨슈머가 느림 → 컨슈머 추가 및 파티션 추가
- **리더와 팔로워로 구성, 리플리카**

## 프로듀서

### 기본 흐름

1. 프로듀서가 데이터를 `send` 시 Serializer가 byte 배열로 변환
2. partitioner를 이용해서 어느 파티션으로 보낼지 결정
3. byte 배열을 버퍼에 배치로 묶어서 저장
4. sender라는 객체가 배치들을 카프카 브로커로 전달

- sender는 별도 쓰레드로 동작
- 배치가 찼는지 여부에 상관없이 sender는 차례대로 브로커에 전송

### 처리량 관련 주요 속성

- `batch.size`: 배치 크기. 배치가 다 차면 바로 전송한다. 배치 사이즈가 너무 작으면 한 번에 보낼 수 있는 메시지의 수가 적어지며 전송 횟수가 많아진다.
- `linger.ms`: 전송 대기 시간(기본값 0). sender가 배치를 카프카 브로커로 전송하기까지의 대기 시간을 의미한다. 대기 시간이 많으면 그만큼 기다렸다가 배치를 전송한다. (예: 3초로 두면 배치가 다 안 찼어도 최대 3초까지는 기다려본다는 뜻)
    - 배치가 그 전에 꽉 차면(`batch.size` 도달) → 3초가 안 지나도 즉시 전송

### 전송 보장과 ack

- `min.insync.replicas`: 브로커 옵션. 프로듀서 ack 옵션이 `all`일 때 저장에 성공했다고 응답할 수 있는 동기화된 리플리카 최소 개수
- 예시) 리플리카 개수 3, `ack = all`, `min.insync.replicas = 2`
    - 리더에 저장하고 팔로워 중 한 개에 저장하면 성공 응답(리더 한 개, 팔로워 중 한 개)
    - 이때, 만약 리더만 전송 성공하고 팔로워가 다 실패하여 최종 전송 개수가 1개일 경우 저장 실패 처리된다.

### 에러 유형과 대응

- **실패 대응 1**
    - `retries`: 재시도 속성. 무한 재시도는 지양
- **실패 대응 2**
    - `send()` 메서드에서 전달한 콜백에서 익셉션을 받는 경우, DB 기록·로그 등 수동 보정 작업

### 재시도와 메시지 중복 전송 가능성

- 프로듀서가 전송하고 브로커가 저장 성공 응답을 보낼 때 타임아웃으로 인해 재시도가 될 경우가 있다.
- `enable.idempotence=true`로 설정하면 Producer마다 고유 ID(PID)와 메시지마다 시퀀스 번호를 붙여서 보낸다. 브로커는 같은 PID + 시퀀스 번호의 메시지가 이미 저장돼 있으면 재전송이 와도 한 번만 저장하고 무시한다. 그래서 "적어도 한 번(at-least-once)"이 "정확히 한 번(exactly-once, 단일 파티션 기준)"에 가까워진다.

### 재시도와 순서

전송 순서: 배치1 → 배치2 → 배치3 순서로 큐에 쌓여 전송 대기 중이다.

**실제 벌어지는 일**

1. 배치1 전송 → 실패
2. (배치1 응답을 기다리지 않고 이미 보내둔) 배치2 전송 → 성공
3. 배치3 전송 → 성공
4. 배치1 재시도 → 성공

결과적으로 브로커에는 **배치2 → 배치3 → 배치1** 순서로 저장된다. 원래 의도는 1, 2, 3 순서였는데 실패 + 재시도 때문에 순서가 뒤바뀐 것이다.

**왜 이런 일이 가능한가**

`max.in.flight.requests.per.connection`이 1보다 크면(기본 5), 배치1의 성공/실패 응답이 오기 전에 배치2, 배치3을 이미 동시에 보내버릴 수 있기 때문이다. 응답을 하나씩 기다리지 않고 여러 개를 동시에 날려서 처리량을 높이는 대신, 먼저 보낸 게 나중에 실패하고 재시도하면 순서가 깨지는 위험을 감수하는 구조다.

**막는 방법**

- `max.in.flight=1`: 배치1 응답이 올 때까지 배치2를 아예 안 보냄 → 순서 보장, 대신 느려짐

**동작 방식 (기본값 5일 때)**

1. 배치1 전송 (ack 대기 중, 슬롯 1/5 사용)
2. 배치1 응답이 안 왔어도 배치2 전송 (2/5)
3. 배치3, 배치4, 배치5까지 응답 안 기다리고 연달아 전송 (5/5, 슬롯 꽉 참)
4. 이제 6번째 배치는 못 보냄 → 5개 중 하나라도 ack가 오면 그 슬롯이 비고, 그때 배치6을 보냄

즉 한 번에 5개를 "쏘고 끝"이 아니라, 항상 최대 5개까지만 미확인 상태로 유지되는 슬라이딩 윈도우다.

**그래서 순서 문제가 생기는 이유**

5개가 동시에 날아가 있는 상태에서, 먼저 보낸 배치1만 실패하고 나중에 보낸 배치2~5는 먼저 성공해버릴 수 있다. 응답이 도착하는 순서 ≠ 보낸 순서가 될 수 있기 때문이다. `enable.idempotence=true`면 브로커가 시퀀스 번호로 이걸 감지해서 순서를 맞춰 저장하고, 꺼져 있으면 그냥 도착한 순서(2, 3, 4, 5, 1)대로 저장된다.

## 컨슈머

### 토픽 파티션은 그룹 단위 할당

- 하나의 컨슈머 그룹에서 컨슈머는 하나의 파티션과 연결되기 때문에, 파티션보다 많은 컨슈머는 놀게 된다. 유의해야 한다.

### 커밋과 오프셋

- 커밋된 오프셋이 없는 경우 `auto.offset.reset` 설정에 따라 동작

### 컨슈머 설정

- `fetch.min.bytes`: 조회 시 브로커가 전송할 최소 데이터 크기
    - 기본값: 1
    - 이 값이 크면 대기 시간은 늘지만 처리량 증가
- `fetch.max.wait.ms`: 데이터가 최소 크기가 될 때까지 기다릴 시간
    - 기본값: 500
    - 브로커가 리턴할 때까지 대기하는 시간으로, `poll()` 메서드의 대기 시간과 다름
- `max.partition.fetch.bytes`: 파티션 당 서버가 리턴할 수 있는 최대 크기
    - 기본값: 1048576(1MB)

### 자동 커밋 / 수동 커밋

- `enable.auto.commit`
    - `true`: 일정 주기로 컨슈머가 읽은 오프셋을 커밋(기본값)
    - `false`: 수동으로 커밋 실행
- `auto.commit.interval.ms`: 자동 커밋 주기
    - 기본값: 5000(5초)
- `poll()`, `close()`: 메서드 호출 시 자동 커밋 실행
- 수동 커밋은 동기 커밋 / 비동기 커밋으로 나뉨

### 재처리와 순서

- 동일 메시지 조회 가능성
    - 일시적 커밋 실패, 리밸런스 등에 의해 발생
- 컨슈머는 멱등성을 고려해야 함
    - 예: 아래 메시지를 재처리 할 경우
        - 조회수 1 증가 → 좋아요 1 증가 → 조회수 1 증가
        - 단순 처리하면 조회수는 2가 아닌 4가 될 수 있음
    - 데이터 특성에 따라 타임스탬프, 일련 번호 등을 활용

### 세션 타임아웃, 하트비트, 최대 poll 간격

- 컨슈머는 하트비트를 전송해서 연결 유지
- 브로커는 일정 시간 컨슈머로부터 하트비트가 없으면 컨슈머를 그룹에서 빼고 리밸런스 진행
- 관련 설정
    - `session.timeout.ms`: 세션 타임아웃 시간(기본값 10초)
    - `heartbeat.interval.ms`: 하트비트 전송 주기(기본값 3초)
        - `session.timeout.ms`의 1/3 이하 추천
    - `max.poll.interval.ms`: `poll()` 메서드의 최대 호출 간격
        - 이 시간이 지나도록 `poll()` 하지 않으면 컨슈머를 그룹에서 빼고 리밸런스 진행

### 주의: 쓰레드 안전하지 않음

- `KafkaConsumer`는 쓰레드에 안전하지 않다(thread-safe 하지 않음)
- 여러 쓰레드에서 동시에 사용하지 말 것
- `wakeup()` 메서드는 예외

**왜 쓰레드 안전하지 않은가**

- `KafkaConsumer` 인스턴스 하나가 브로커와의 네트워크 연결, 수신 버퍼, 파티션별 오프셋 위치를 내부 상태로 함께 들고 있다.
- `poll()`은 이 상태를 읽고 쓰는 동작이라, 두 쓰레드가 동시에 호출하면 버퍼와 오프셋이 서로 덮어써진다.
- 그래서 `KafkaConsumer`는 메서드 진입 시 현재 사용 중인 쓰레드 ID를 기록해 두고, 다른 쓰레드가 들어오면 `ConcurrentModificationException`을 던진다.
- 락을 걸고 기다려 주는 게 아니라 그 자리에서 예외 → 컴파일 타임이 아니라 런타임에 터진다.

**`wakeup()`만 예외인 이유**

- `poll(timeout)`은 데이터가 없으면 블로킹되기 때문에, 밖에서 종료를 알릴 수단이 반드시 필요하다.
- `wakeup()`은 내부 플래그를 세우고 네트워크 셀렉터를 깨우기만 한다 → 컨슈머 상태를 건드리지 않아 다른 쓰레드에서 호출해도 안전하다.
- 호출되면 블로킹 중이던 `poll()`이 `WakeupException`을 던지며 즉시 리턴 → 이걸 잡아서 `close()`로 마무리하는 게 표준 종료 패턴이다.
- `close()`는 남은 오프셋 커밋 + 컨슈머 그룹에서 정상 탈퇴까지 처리해 준다.

**그럼 병렬 처리는 어떻게 하나**

- **방법 1. 쓰레드마다 `KafkaConsumer`를 따로 생성 (1 쓰레드 = 1 컨슈머)**
    - 구현이 단순하고 커밋·순서 관리가 그대로 유지됨. 보통 이 방식을 권장
    - 단, 파티션 수보다 많은 컨슈머는 할당을 못 받고 놀게 됨
- **방법 2. `poll()`은 한 쓰레드에서만 하고, 레코드 처리만 워커 쓰레드 풀에 위임**
    - 처리량은 올라가지만 파티션 내 순서 보장이 깨지고, 오프셋 커밋 시점을 직접 관리해야 함
    - 처리가 끝나기 전에 커밋하면 장애 시 메시지 유실, 워커가 밀리면 `poll()` 간격이 `max.poll.interval.ms`를 넘겨 리밸런스 발생
    - `pause()` / `resume()`으로 특정 파티션 조회를 잠시 멈춰 완충할 수 있음
